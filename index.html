Data Processing Models

4th October 2026

Explore the three fundamental paradigms of how computing systems handle data, trigger execution, and manage latency.

📦

Batch Processing

Grouped data processed in bulk on a schedule. It is designed for background execution where tasks are queued up and run all at once.

Latency: High (Hours/Days)
Throughput: High
Latency Tolerance: High (Hours/Days)
Throughput Focus: High volume efficiency
Human Role: None during execution
💬

Interactive Processing

User-driven, synchronous feedback loop. A user issues a command and waits for the system to process it and return a response immediately.

Latency: Low (Seconds)
Trigger: User Command
Latency Tolerance: Low (Seconds)
Throughput Focus: Single transaction speed
Human Role: Drives the process actively
⚡

Real-Time Processing

Event-driven continuous stream processing. System reacts to continuous streams of data the exact instant they are generated.

Latency: Ultra-low (Milliseconds)
Trigger: Continuous Events
Latency Tolerance: Zero to Ultra-low (Milliseconds)
Throughput Focus: Immediate event reaction
Human Role: None (Automated system response)

Real-time does not mean real fast

Predictable

A real-time system is one whose timing can be guaranteed, not one that is simply quick.

  • Slow but real-time — A weather station that must log a reading every 10 minutes is a real-time system.

  • Fast but not real-time — A gaming PC is extremely fast, but Windows cannot guarantee when your program runs.

  • Averages hide danger — A controller that responds in 1 ms on average but 200 ms once a day will eventually miss a 10 ms deadline.

  • Worst case matters — Designers must know the longest possible response time.

Field Exercise No. 1

Worked example: is the deadline met?

A sensor task is released at t = 100 ms; its relative deadline is 10 ms.

  1. 100

    Released

    The sensor interrupt arrives. The task is ready to run at t = 100 ms.

  2. 103

    Starts

    Another task was using the CPU, so it starts 3 ms later (waiting time 3 ms).

  3. 109

    Finishes

    It needs 6 ms of CPU time, so it finishes at t = 109 ms.

  4. 110

    Deadline

    Absolute deadline = 100 + 10 = 110 ms.

    Response time = 9 ms ≤ 10 ms: met.

Field Observation Note

If the other task delays it by 5 ms instead of 3, the response time becomes 11 ms and the deadline is missed, without any change to this task's own code.
